ISO/IEC 25010:2023 の製品品質モデルは、すでに9特性ある。2011年版の8に足された9番目は安全性（Safety）だ。使用性は相互作用能力に、移植性は柔軟性に名前が変わった。

9番目の席は埋まっている。筆者が足りないと思うのは、残ったときの危害だ。終わらせ方の品質。名前は deletable でよい。

> 良いソフトウェアとは、AI が下手な作業を要求しないソフトウェアである。

下手な作業は、結合した既存コードへの部分改修だ。上手な作業は、境界の内側をまるごと捨てて生成し直すこと。deletable はその境界と捨て方の品質である。

## 進化の安い経路は、消して作り直すこと

いまの生成 AI は、新規の文書も新規の実装も安い。既存コードの一点を触って、波及を読むのが高い。だから進化の安い経路は、単位を捨てて作り直すことになる。

消せないソフトウェアは、一番高い作業を人間と AI の両方に強制する。それが品質特性になる理由だ。

Joel Spolsky が全面書き換えを戒めたのは、人間が暗黙知を失う前提だった。再生成のコストが下がったいまも、全面作り直しは死ぬ。ここで言う差し替えは、単位ごとに捨てて入れ直すことだ。

「AI が修正下手」をツールの不平で終わらせると、モデル待ちの話になる。品質の話にするなら、ソフトウェア側が「触る」を要求しない形へ寄る。

## 許可されている操作は、足すか、途中から捨てるか

中身を操作に落とすと、こうなる。許可されているのは **append** と、分岐点から先を捨てて作り直すことだけだ。その場で書き換える操作は、品質として高いコストを払う。

コンパイラは命令型の代入を SSA に直し、代入のたびに新しい名前を振る。時間を名前にしている。関数型の immutable も同じで、更新は新しい値を返すことであり、元の値は残る。エイリアスを追わなくてよい。

可変だと、`f(x)` のあと `x` が同じ物かは `f` の中を見ないと分からない。別名で指している全部も見る。並行なら他スレッドも見る。人間にもモデルにも高いのは、この追跡だ。関数を丸ごと捨てて差し替えても、呼び出し側が持っている値が壊れない言語は、AI が下手な作業を言語側で消している。

ここを「AI は Haskell が得意」と書くと外れる。生成の流暢さは訓練データの話で、純粋関数型はベンチではむしろ弱いことがある。安全に捨てて差し替えられる形の話と、生成の上手さは別だ。

## Excel が唾棄された理由は、作れても消せないこと

エンジニアが業務フローに埋め込まれた Excel を嫌ったのは、UI でもマクロでもない。業務の真実が、一枚のシートに吸われることだ。

セルは上書きされる。誰がこのセルを参照しているかは、別シート、別ファイル、メールの添付まで見ないと分からない。エイリアス問題そのものだ。`最終_v3.xlsx` が増えるのは版管理ではない。過去を書き換えられないから、コピーで逃げている。

ファイルとしては消せる。システムとしては消せない。ロジックとデータの核がそこ以外に無いから。キーパーソンが数式を頭に持っているのも同じで、核がテストにも契約にも落ちていない。

Excel は作るのが安い。触るのが高い。AI の得意不得意と同じ形をしている。唾棄は品質の判定だった。消せない。ソースデータから毎回捨てて再生成するシートなら、投影なので消してよい。嫌われるのは、投影が本体に昇格したときだ。

## KV キャッシュは、モデル自身がそう動いている

推論側の物理が、すでにこの制約で動いている。

各トークンの Key / Value は、それより前の全部に条件付きで、位置が付いている。生成は末尾に足すだけだ。途中のトークンを「ちょっと直す」操作は、仕様に無い。位置 N を変えたら、N 以降は全部無効になる。

llama.cpp がやっているのは、共通の先頭を残し、後ろを切って、そこから計算し直すことだ。プロンプトの先頭を少しいじるとキャッシュが死ぬのも同じで、変化が末尾以外に漏れた失敗例である。

つまり LLM 自身が、過去は触らず、足すか分岐点から捨ててやり直すか、以外の進化経路を持っていない。既存コードの外科手術が下手なのは、ツールの未成熟だけでなく、計算グラフがそうなっている。

## スキルは、次のモデルで負債になる

しゅうへい氏が [GPT-6 Astra について書いていた](https://x.com/shupeiman/article/2096565809556681138)一行が、この話の今の断面だ。スキルを細かく入れるほど動きが悪くなる。Opus 5 のときと同じで、いまの主流は「そこまで書くな」だという。

陳腐化ではない。使われなくなった道具なら、放置でもいい。残っていると、新しいモデルの既定動作を上書きして成績を下げる。負債だ。Excel と同じ形で、ファイルは消せるのに「うちのやり方」として核に昇格しているから消せない。

古いモデルのギャップを埋めた手順は、ギャップがモデル側に吸われた瞬間、先頭の汚染になる。KV と同じで、古い指示が以降全部を条件付ける。モデルが指示なしで動き始めたら、指示の在庫そのものが書き換えになっている。

「詳しく書くほど品質」は保守性の直観だ。こちらは逆で、モデルが推論できる手順は書いてはいけない。書くのは、モデルが知り得ない核だけだ。目的、制約、この環境だけの事実。手順、口調、回避策は本体で、モデル世代と一緒に捨てる。

スキルの価値は、対象モデルが消えたときに一緒に消せるかで測る。消せないスキルは、次のモデルに対する欠陥である。

## 消してよい本体と、消してはいけない核

全部消せて再生できると、本番でしか得られない傷まで消える。障害の痕跡、例外、運用判断。だから対になる命題が要る。

| 残す核 | 捨ててよい本体 |
| --- | --- |
| テスト、契約、失敗の記録 | 実装 |
| ソースデータ | Excel のシート |
| 安定した prefix | KV の suffix |
| 目的・制約・環境の事実 | スキルの手順 |

Event sourcing のログが「消せない」ことと矛盾しない。ログは核だ。投影は捨てて再構築する。核が残っているから、捨てて再生成しても品質が戻る。

## 保守性の下に置かない

この特性を保守性や柔軟性、セキュリティの副特性に落とすと、消える。保守性は直し続ける前提、柔軟性は別環境で生き続ける前提、セキュリティは守る前提だ。終わらせる操作の品質は、そこに収まらない。

測るなら、二つで足りる。単位を消したとき、再生成に必要な核は明示されているか。途中の変更が、suffix を捨てる以外の経路を要求しないか。前者は設計、後者は実行時の形だ。

10番目を名乗るなら、終わり方を一等の特性として置け。足すのが飽和したあとに残るのは、消せないものだけだ。
