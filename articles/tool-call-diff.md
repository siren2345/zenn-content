# Claude Code と opencode のツール呼び出し構造の違い

`qwen3-coder:30b` などの大規模言語モデル（LLM）を用いたエージェント開発において、**ツール呼び出し構造の互換性**は重要です。特にコンテキスト長が256Kを超えるモデルでは、外部情報取得（WebFetchなど）が不可欠であり、動作原理の違いが大きな差になります。

この記事では、現時点での Claude Code と opencode のツール呼び出し構造を比較します。

---

## ツール呼び出しのプロトコル違い

### Claude Code の特徴
- `{"name": "WebFetch", "arguments": {...}}` という独自 JSON Schema を使用
- LLM（例：`qwen3-coder:30b`）が XML 形式で出力 → 不一致
- モデル呼び出しプロトコルの不整合により誤読に至る

### opencode の仕組み
- `WebFetch`, `Write`, `Read` などの標準ツール形式を持つ
- LLM 出力形式が構造化されやすく、JSON ツール呼出に対応可能
- ローカルLLMとの連携が良好

---

## コンテキスト長処理の違い

### Claude Code の問題点
- 設定ファイル（`settings.json`）により環境変数上書きが発生
- 指定したコンテキスト長は無視されやすく（65.5Kに固定）
- 大量テキストが処理できず、エージェントとして動作不可

### opencode での対策
- `opencode.jsonc` で明示的なコンテキスト長設定可能（例: `262144`）
- `OLLAMA_CONTEXT_LENGTH` のような環境変数が有効で、正確な窓が維持される
- これにより大規模な文章処理も安定

---

## 実際の運用比較

### Claude Code
- WebFetch が誤読 → システムエラー・非効率な情報取得
- モデルが「返事をする」だけ → 統一されたツール利用が困難

### opencode
- `WebFetch` の正確な動作により、外部情報の取得・処理が可能
- 実運用レベルのエージェントとして安定稼働

---

## まとめ

ローカルLLMによるエージェントの構築では、**コンテキスト長とツール呼び出しプロトコルの互換性**が鍵になります。今回の検証結果より：

- `qwen3-coder:30b` を用いる場合、opencode の方がツール構造が適応的
- Claude Code は動作が不完全 → モデルとツールの形式がマッチしていない
- 本番運用では opencode の利用を推奨

---
